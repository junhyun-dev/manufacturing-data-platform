**2026-09-08 외부 조사·원본 점검 완료 / 사용자 결과 중심의 제품화 방향 수용.** 작성자는 기술 시연에서
사용자 결과·복구·반복 사용으로 발전시키고 여러 세션에서 이어가는 방향에 동의했다.
이후 작성자는 직접 사용할 수 있는 첫 서비스를 구현하도록 위임했다. CSV 검토·구간 분석·수정 파일·보관 원본 복구의
구체적인 첫 정책은 [파일 계약](../FILE_REVIEW_CONTRACT.md)으로 수용했고, 시장 수요는 여전히 검증할 가설이다.
첫 사용자, 기존 업무의 비용, 반복 사용, 기존 대안보다 나은 결과는 확인하지 못했다. 실제 담당자·운영 데이터에
접근할 통로도 아직 확인되지 않았다. 아래 공개 데이터 검증안을 출발점으로 삼되 실제 사용자 검증과 구분한다.

## 검증할 제품 가설

설비 기록을 분석가에게 제공하는 데이터 담당자가 **요청받은 시간 구간을 전달해도 되는지 확인하고,
누락·정정 후 같은 분석 결과를 다시 전달하는 작은 데이터 제품**을 후보로 둔다. 소비자의 첫 질문은
“선택한 시간 구간의 압력·온도·전류 요약은 어떤 원본과 관측 범위를 사용했고, 다시 계산할 필요가 있는가?”다.
당시 기존 `PUBLISH/BLOCKED/REPROCESS REQUIRED` 실험에서 분석 결과·복구 행동을 연결하는 방향을 탐색했다.
이후 수용한 CSV 서비스는 기존 OPC UA 경로와 별도의 파일 계약으로 구현했다.

수용한 첫 파일 계약에는 범용 historian, 제조 KPI 서비스, 예지보전 모델이 포함되지 않는다.
실제 첫 사용자는 연구용 데이터를 다루는 분석가일 수도 있다. 그런 검증을 공장 운영자의 수용으로 바꾸지 않는다.

CSV 1,516,948행을 physical order대로 읽고 timezone을 부여하지 않은 timestamp 차이를 계산했다.

- 첫/마지막 시각: `2020-02-01 00:00:00` / `2020-09-01 03:59:50`.

## 더 단순한 대안과 비교

| 대안 | 먼저 비교할 이유 | 선택을 바꿀 조건 |
|---|---|---|

| 기존 historian / SiteWise의 질의·복구 기능 | 수집·격리·집계·정정을 이미 제공하는 실제 대안 | 사용자 환경에서 기존 기능을 연결하는 편이 낫다면 재사용. 새 플랫폼 구축을 목적화하지 않음 |
| 현재 trust 구현 + 소비자 결과 + 범위 복구 | 기존 source·발행 검증을 실제 전달 업무에 사용할 후보 | 사용자가 버전·누락 범위·복구 결과 확인에 반복적인 어려움을 겪는지 먼저 확인 |

숫자는 실제 기록이고 누락·중복·quality 변형은 실험 주입이다. 운영 효율이나 장비 건강에 대한 결과도 아니다.

## 사용자 검증과 중단 조건

1. 담당자에게 최근 실제 사례 한 건을 확인한다: 어떤 분석 결과를 기다렸는지, 누락·정정을 어떻게 알았는지,
   현재 도구와 수작업은 무엇인지, 잘못 전달하면 어떤 일이 생기는지. 기능 선호보다 기존 행동을 확인한다.
2. 같은 입력·정상/불완전/복구 시나리오로 단순 기준선과 제품 후보를 비교한다. 작성자의 설명 없이 올바른
   구간·버전을 고르는지, 걸린 시간·도움 요청·잘못된 선택을 기록한다. 절감률 목표나 사용자 성과를 미리 만들지 않는다.
3. 다음 구간에서도 다시 사용하고 싶은 이유와 걸림돌을 받는다. 외부 개발자의 재현 성공은 기술 검증,
   실제 업무 담당자의 반복 사용은 제품 가치 검증으로 각각 기록한다. 현재 둘 다 미실행이다.

첫 외부 검증 후보는 데이터 엔지니어/분석가 1명, 접근 가능하면 제조·설비 담당자 1명이다.
이는 조사 제안이며 메시지 발송이나 참여 수락이 아니다. 접근할 사람이 없으면 공개 데이터·독립 SQL 실험을
계속할 수 있지만 실사용 검증을 통과한 것으로 처리하지 않는다. 첫 usable version 뒤에도 실제 업무와 기존 대안의
빈틈을 찾지 못하면 범위를 로컬 품질·발행 도구로 유지한다. 제품 필요가 없는 기능 추가로 이를 보상하지 않는다.

### 공개 화면에서 관찰한 패턴

2026-09-10 공식 문서와 문서에 게시된 이미지 원본을 열어 확인했다. 로그인한 제품을 직접 조작한 결과가 아니다.

### 소수 대안과 추천

| 대안 | 잘 해결하는 질문 | 현재 데이터 적합성·대가 | 선택 판단 |
|---|---|---|---|
| A. 상태 카드 + 검사 사건 목록 + 기존 시계열 | 최근 전달은 어땠고 어떤 결과가 남았나? | 기존 데이터만으로 명확하며 좁은 화면에 유리. 설비·항목 관계를 발견하는 힘은 작음 | 가장 단순한 비교 기준. 관계도가 도움을 주지 않으면 이쪽으로 축소 |
| B. 작은 설비 데이터 지도 + 연결된 상세 **추천** | 이 설비 그룹에 어떤 측정 항목이 있고, 선택한 결과의 근거는 무엇인가? | 현재 버전의 그룹–항목 소속 관계로 가능. 선택·시간 범위·이전 결과를 일치시켜야 함 | 사용자가 원하는 시각적 탐색을 실제 파일 근거 안에서 시험할 수 있음 |
| C. 전체 설비 버블망 + 상태 시간 띠 | 어느 설비의 이상이 어디로 퍼졌나? | 실제 자산 식별·연결 종류·상태 판정·시간 근거가 먼저 필요. 모바일 탐색과 오해 비용이 큼 | 보류. 노드 수를 늘리려고 가상 공장을 만들지 않음 |

현재 세 항목은 기존 선택 상자로도 찾을 수 있다. 지도의 추가 가치 가설은 처음 온 사람이 항목의 묶음과 근거 이동을
더 쉽게 발견한다는 것이다. 이는 아직 관찰되지 않았으므로 B는 작은 사용성 실험으로 제한하고, 새 분석 능력으로 홍보하지 않는다.

### 한 사용자 장면과 화면 구상

데이터 담당자가 공개 압축기 기록으로 분석 결과를 전달하려 한다. 샘플 전달 실험 후 경고를 보고
“온도 데이터도 사라졌나, 지금 내려받는 것은 어느 파일인가?”를 확인한다. 설비 그룹에서 Oil_temperature를
선택해 남아 있는 관측·버전·원본을 읽고, 같은 조회의 ZIP을 전달한다. 설비의 고장 여부는 이 과제의 판단이 아니다.

아래는 **제안 wireframe**이다. 배치는 미구현이며 `vA`는 실제 hash를 대신한 기호다.
수량·날짜는 위 공개 샘플, 누락은 기존 합성 전달 실험에 근거한다. 선은 물리적 흐름·인과·상관관계가 아니다.

```text
MetroPT-3 · 2020-02-01                  [원본·버전 근거]
원본 관측: 00:00:00–23:20:21 / 시간대 미제공 / 과거 기록
[현재 검토 결과: vA 유지] [최근 전달: 실험 미완료] [설비 건강: 판단 근거 없음]
최근 전달 실험: 기대 21,432개 중 2,143개 제외 / 현재 결과는 21,432개

파일 안 설비             이 버전에 기록된 측정 항목           선택 항목 상세
> MetroPT-3 APU          ○ TP2 · bar                         Oil_temperature · °C
  측정 항목 3개          │                                  조회 버전: vA
                        ○ MetroPT-3 APU ── ◎ Oil_temperature [시작 포함 / 종료 제외]
                        │                     °C           [조회]
                        ○ Motor_current · A                기존 실제 관측 그래프
                                                           전체 구간 관측 7,144개
선의 의미: 같은 파일 버전에서 이 설비 이름으로 기록됨          [결과 설명] [같은 결과 ZIP]
원본의 자산 ID·설비 간 연결 자료 없음                        품질 미제공 7,144개

최근 검사 사건 (서버 처리 시각, 원본의 2020년 시간축과 별도)
○ 최초 입력 수용: vA   ○ 전달 실험 미완료: vA 유지
[각 사건의 실제 시각·검사 근거] · 최근 표시 범위만, 전체 감사 이력 아님
```

선택 항목은 외곽선과 `선택됨` 문구로 구분하고 노드는 같은 크기를 쓴다. 노란 경고는 **파일의 최근 전달 상태**다.
측정 항목별 문제 위치를 계산하지 않았으므로 해당 설비나 온도 노드를 고장 색으로 칠하지 않는다.
노드 수량을 표시한다면 `이 버전 전체 관측 수`라고 붙이고 선택 구간 집계와 분리한다.

데스크톱에서는 지도와 상세를 나란히 둔다. 작은 화면은 상태 카드 → 설비 이름 → 같은 항목 목록 → 선택 상세 순서로
쌓고 지도를 펼치는 방식이 후보이며, 가로 끌기나 hover가 있어야만 근거를 읽게 하지 않는다.
목록과 지도는 동일한 선택을 사용한다. [W3C 색상 사용 설명](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)에
따라 색에만 의미를 맡기지 않고 이름·관계·상태를 문자로 제공한다. 키보드 선택·포커스·읽기 순서는 구현 뒤 확인할 항목이다.
기존 결과 설명 패널과 새 상세 패널을 동시에 겹치지 않게 하고, 설명을 닫으면 원래 선택 항목으로 돌아오게 하는 것이 후보다.

### 첫 구현 후보와 검증 경계

아래는 **선택 전 검토한 후보 기록**이다. 이후 수용된 정확한 범위는 위 지도 계약을 따른다. 구현 완료 기록은 아니다.

- Data: 현재 한 workspace·한 dataset·한 검증 버전의 `current.series`로 설비 이름과 항목의 소속을 읽는다.
  화면 식별은 `(dataset_id, version, equipment)` 및 tag/unit 조합으로 한정한다. 이름이나 원본 hash만으로 다른
  파일·workspace를 연결하지 않는다. 기존 `model.py`의 검증·`store.py`의 소유권과 무결성 확인이 권위다.
- API·계산: 기존 dataset/query/export/explanation 경로를 재사용하는 것이 첫 후보다. 지도는 새 SQL·통계를 만들지
  않으며 상세는 `query.py`의 전체 선택 집계를 쓴다. 설비·항목 선택 후 기존 조회 조작을 유지한다. 버전·필터·최신 시도
  맥락이 바뀌면 이전 상세와 다운로드를 새 선택의 결과처럼 표시하지 않는다. 다른 탭의 교체도 응답의 버전/시도 ID로 대조한다.
- UI·규모: 한 번에 한 설비 그룹과 가까운 항목만 표시한다. 큰 파일에서도 모든 항목의 통계를 자동 병렬 조회하지 않는다.
  제안 상한은 측정 항목 8개와 중심 1개이며 나머지 수를 명시하고 전체 항목 목록으로 선택할 수 있게 한다.
  그래프 DB·새 서버·외부 라이브러리 도입은 이 관계를 표현하기 위한 선행조건이 아니다.
- 시간·사건: `current.range`는 원본 관측 시간, `latest.at`·history는 서버의 검사 시각이다. 현재 API의 최근 12개
  사건을 실제 시각과 상태로만 표시한다. 생략된 이력·보존 만료를 감추거나 가동 시간 띠·고장 빈도로 바꾸지 않는다.
- 실패·수명: current 없음/무결성 실패면 지도를 이전 기억으로 복원하지 않는다. 정상적인 이전 결과 유지는 별도 표시한다.
  0개 구간은 0/null로 남긴다. 삭제·만료·권한 거부·늦은 응답은 기존 거부/취소 경계를 따르고 재조회로 복구한다.
  CSV 이름은 계속 불신 텍스트로 렌더링한다. 외부 전송·관계 편집·공장 제어·대화 저장은 포함하지 않는다.

수용 뒤에는 [파일 계약](../FILE_REVIEW_CONTRACT.md)의 선택·화면·오류 의미와 affected UI/API/tests를 함께 닫는다.
현재 구현 위치는 [Architecture](../ARCHITECTURE.md), `current.series`는
[`model.py`](../../src/manufacturing_data_platform/file_review/model.py), 버전/사건/권한은
[`store.py`](../../src/manufacturing_data_platform/file_review/store.py), 집계/ZIP은
[`query.py`](../../src/manufacturing_data_platform/file_review/query.py)가 소유한다.

첫 완료 증거는 공개 샘플의 **항목 선택 → 같은 버전의 통계 → 원본 근거 → ZIP** 한 흐름이다.
독립 기대값·실제 HTTP/브라우저·모바일/키보드에서 다음 반례를 확인해야 한다: 전달 실패를 설비 고장으로 오인,
다른 파일의 같은 설비 이름을 합침, 선택 변경 뒤 늦은 응답이 새 결과를 덮음, 무결성 오류 뒤 오래된 지도가 남음,
8개 초과 항목을 숨긴 채 전부라고 표시, empty 구간에 이전 평균이 남음. 다중 설비 테스트용 자료는 합성 fixture로 표시한다.

### 남은 선택과 다음 근거

2026-09-10 작성자는 **B의 ‘현재 파일 안 설비 그룹–측정 항목 지도’부터 로컬 구현**하는 추천을 수용했다.
실제 설비 건강·설비 간 물리 연결이 먼저 필요하다면 구현보다 자산 식별/관계 원본과 판정 근거를 확보하는 조사가 다음이다.
DB나 그래프 라이브러리 선택은 수용 범위 내 기술 판단이다. 물리 연결·설비 건강 모델과 공개 발행은 수용에 포함하지 않는다.

MFG-09/MFG-12의 미완료 사용성 검증은 유지한다. 현재 화면에서 먼저, 이후 후보가 구현되면 같은 과제로
“전달 실험 뒤 온도 결과와 같은 버전의 근거를 찾아 전달해 주세요”를 제시하고 잘못된 버전 선택·도움 요청·
원본과 처리 시각의 혼동·소요 시간을 관찰한다. 한 사람의 재수행에는 학습 효과가 있으므로 속도 차이만으로 개선을
주장하지 않는다. 지도 때문에 의미를 더 잘 찾지 못하거나 정상/고장 오해가 늘면 A로 축소한다. 공개 샘플 성공만으로
여러 설비 업무·시장 적합성·공장 도입을 주장하지 않는다. 외부 사용자 섭외·공개 배포는 별도 승인 범위다.

**추천 최소 변경은 ‘검토 화면 넓게 보기 + 전체 항목 이름 검색’, 지원 환경의 전체화면 버튼이다.**
설비의 온도 항목을 찾는 사람이 이름을 확인하고, 고른 항목의 관측과 같은 버전 근거를 계속 옆에서 읽게 한다.
넓게 볼 대상에 지도·선택/조회·관측·출처/ZIP을 함께 포함한다. 지도만 화면을 차지해 상세를 찾으려면 닫아야 하는 흐름은 피한다.

| 대안 | 해결하는 문제 | 대가와 선택 |
|---|---|---|
| 기존 목록·페이지 스크롤 유지 | 세 항목을 빠르게 고르고 익숙한 방식으로 내려 읽음 | 추가 기능 비용이 가장 작음. 긴 목록 탐색과 지도/상세 왕복은 남음. 비교 기준·항상 가능한 fallback |
| 넓게 보기 + 선택적 브라우저 전체화면 | 주변 파일 목록 공간을 줄이고 긴 이름·지도·관측을 함께 읽음 | 세로 스크롤 자체는 남을 수 있고 작은 화면의 물리 크기는 늘지 않음. 이탈/포커스·설명 패널 처리가 필요. 첫 변경 추천 |
| 전체 항목 이름 검색·선택 | 8개 밖의 특정 항목을 찾음 | 검색 결과 목록이 추가되지만 현재 설비/버전의 metadata만 이용 가능. 위 변경에 포함하되 기존 select 유지. 검색만으로 현재 선택/통계를 변경하지 않음 |
| 지도 확대·축소·이동·맞춤/초기화 | 큰 작업면의 일부를 자세히 보거나 길을 잃었을 때 전체/선택 위치로 돌아옴 | 축소는 글자/버튼을 작게 만들고, 드래그는 페이지 스크롤·선택과 충돌할 수 있음. 현재 8개 상한/이름 생략은 해결하지 않음. 첫 변경 후 실제 공간 탐색 불편이 남으면 선택 |

첫 후보의 개략 구상이다. `N/m`은 수량 자리표시자이며 실제 새 데이터·구현 화면이 아니다.

```text
[기본 화면으로] 파일 · 설비 · 결과 버전                 [전체화면]
[항목 이름 찾기________] 검색 m / 전체 N [검색 지우기] [기존 전체 목록]
[현재 지도: 최대 8 / N]       [선택 항목 전체 이름·단위]
[같은 파일 안 소속 관계]     [기존 조회 조건 · 조회] → 관측 그래프
                            [출처·버전 근거] [같은 조회 ZIP] [결과 설명]
```

기술 추천은 기존 HTML 버튼·SVG·CSS 배치를 재사용하는 것이다. `넓게 보기`는 일반 문서 배치 전환으로 두고,
선택적 Fullscreen API는 설명 패널·toast·삭제 dialog까지 포함하는 문서 루트를 대상으로 검토한다. 현재 설명 패널은
`application-shell` 밖에 있어 지도나 shell만 fullscreen으로 만들면 기존 설명 경로를 가릴 수 있다.
별도 overlay·복제 DOM·canvas renderer·graph DB·API·라이브러리는 첫 후보에 필요하지 않다.

**구현을 선택할 경우 수용 기준 제안:** 아직 [현행 계약](../FILE_REVIEW_CONTRACT.md#equipment-data-map--first-local-view)의 변경은 아니다.

1. 넓게 보기/전체화면 진입·이탈은 dataset/version/latest attempt, 설비·항목, 제출 범위·결과·ZIP을 바꾸거나 조회를 발사하지 않는다.
   데이터 없음에서는 진입 안내, 실패/만료/삭제/무결성/다른 탭 상태 변화에서는 기존 무효화가 넓은 화면에도 적용된다.
2. 검색은 현재 파일 버전·선택 설비의 모든 항목을 이름 부분 일치로 찾는 metadata 필터 후보다. 결과 개수·검색 0건·지우기와
   전체 이름을 제공하고 기존 목록은 유지한다. 검색어 입력/지우기만으로 선택을 바꾸지 않는다. 결과를 명시적으로 선택할 때만
   기존 항목 전환 규칙을 적용하며, 지도 최대 8개/전체 수·선택 항목 포함을 유지한다. 파일/설비 전환은 검색어를 초기화한다.
3. 전체화면 요청 실패/미지원은 넓게 보기로 남기고 이유를 알린다. 보이는 나가기 버튼과 Esc/시스템 이탈을 실제 상태에 동기화한다.
   이탈 후 선택·제출 구간과 원래 조작 위치를 유지한다. 설명 dialog와 삭제 확인창의 Esc/포커스가 함께 처리되지 않게 검증한다.
4. 1440/390/320px·가로/세로 전환·브라우저 글자 확대에서 이름/버튼/목록/상세에 접근한다. Tab/Enter/Space와 탭만으로 완료하고,
   모바일 기본 스크롤·브라우저 확대를 가로채지 않는다. 기본 화면의 같은 과제도 유지해 도움 요청·버전 오류·왕복·소요 시간을 비교한다.
5. 실제 3항목 샘플과 합성 8/11/50/200항목·128자까지의 긴/유사/markup 이름을 구분해 시험한다. 검색/배치만으로 서버 query가
   증가하지 않는지, 명시적 항목 선택→관측→출처→ZIP의 version/조건/hash가 유지되는지 확인한다. 새 성능/지원 규모 약속은 실측 전 미정이다.

후속 카메라를 선택하면 `+/-`·배율, 드래그 없는 이동 대안, **표시된 항목 맞춤**(숨은 항목까지 뜻하지 않음),
선택 항목으로 이동·초기화의 의미를 먼저 닫는다. 포커스가 화면 밖에 남지 않고 선/노드가 같은 좌표계를 쓰게 하며,
배율 하한은 글자·조작 크기를 검증해 정한다. reset은 시야만 바꾸고 query·검색어·선택을 지우지 않는다.
이것은 첫 후보의 구현 선행조건이 아니며 8개 상한을 풀거나 물리 관계를 추가하는 승인도 아니다.

이번 반환의 선택은 추천한 첫 탐색 범위를 로컬 구현할지 여부다. 기존 사용성 관찰과 Release는 이 후보와 독립적으로 진행할 수 있다.
Main이 직접 읽기·비교를 마쳤고 추가 Worker 작업은 열지 않았다. 문서 링크·diff·source 불변 확인만 수행하며,
새 runtime/test 통과·실제 사용자 관찰·배포를 주장하지 않는다.
